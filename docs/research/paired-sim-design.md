# Design record: paired client-server simulation (integrated server rework)

Written 2026-08-14. Status: accepted design, pre-implementation. Origin: the slime damage boost investigation (branch feature/allow-damage), the lagback problem, and the block interaction ticket (mid-run trapdoor flips, today done by hand as flip-then-resimulate-from-checkpoint). Decision driver: the simulation entity must behave like the real player, server included, so TASers can stumble on tech they did not know existed because the entity behaves "strangely" while building a TAS. Nothing in this design requires a glitch to be understood before it reproduces.

Verification status: the [verify] pass for loader-fabric ran on 2026-08-14 against the local 26.2 loom sources (mapping set 0e74ef6db8), before the corresponding code was written. Every marked claim was confirmed or corrected; section 13 is the record. The loader-fabric-1.21.3 port ran its own surface pass on 2026-08-15 against the module's deobfuscated client jar; section 14 records the deltas. The forge loaders ran theirs against their genSources output before their ports were written: 1.8.9 on 2026-08-15 (section 16), 1.12.2 on 2026-08-16 (section 17). All four loaders now carry the pair and lockstep.

## 0. Problem: the trick class is unrepresentable in a single-entity sim

In vanilla, one block sample decides both halves of a landing. After collision resolution, Entity movement samples the single block roughly 0.2m below the player's center [verify: exact offset and fence special case per version], and that one block drives both the fall damage decision (onFallenUpon, which slime negates unless sneaking) and the bounce (onLanded, motionY inversion). One entity in one world therefore gets damage XOR bounce, never both. No amount of letting damage through to SimulatorEntity (the feature/allow-damage approach) can express "took fall damage AND bounced".

The real trick lives in the client-server split. The client decides its landing mid-tick at the collision position. The server does independent fall bookkeeping in its move-packet handler, fed by the client's end-of-tick reported positions and onGround flags, sampling below the reported center [verify: handler fall path per version]. Edge landings can make the two samples straddle the slime edge: the client bounces, the server rules fall damage, damage marks the server entity velocityChanged, and the server flushes a velocity packet whose payload is the server entity's motion at that moment [verify: flush site and payload per version]. The client overwrites its motion with that payload when the packet queue drains at a tick boundary [verify]. The observed "very high bounce" is the interaction of the preserved client bounce and that packet; this record deliberately does not claim which part dominates, because the design reproduces it without needing to know.

The same handler contains the vanilla movement checks (moved too quickly, moved wrongly) whose correction teleport is the singleplayer flavor of the lagback. And a mid-run trapdoor flip is a server-side world mutation triggered by a click the input rows already record. All three features are the same shape: server-originating effects landing on the client at tick boundaries.

## 1. Decision

Build a lockstep client-server pair under the simulator's control, singleplayer only. The current client-style SimulatorEntity keeps doing client physics; a persistent fake server player in the WorldServer, wired to a real server-side network handler over a local channel, does the server's half; the sim loop carries synthesized packets between them at fixed, deterministic boundaries. The simulation remains the single source of truth; it now computes the truth of the pair, not of one entity.

Rejected alternatives, with dispositions:

1. Declared per-tick event track (velocity set, position set, block set as user-declared inputs). Rejected as the primary mechanism: declared events can only express tech somebody already understands, which is backwards from the emergence goal. The idea survives inverted, as the diagnostic event log the paired sim emits (section 10).
2. Shadow prediction (reimplementing the server's fall bookkeeping as a core pure function per version). Rejected: per-version physics reimplementation that drifts from MC with every update. The pair reuses each version's real server code instead.
3. Multiplayer support for desync tech. Rejected by decision: MP timing is not deterministic, and the project only wants these glitches supported in singleplayer.
4. Isolating the sim in a separate world. Rejected: the entity mutating the real world is desired, the player watching the run should see the trapdoor flip and every other consequence of the current TAS.
5. RNG pinning at checkpoints. Withdrawn: see the invariant in section 3; no supported mechanic reads RNG into an outcome, so there is nothing to pin.

## 2. Architecture: the lockstep pair

Components, per loader:

- Client entity: the existing SimulatorEntity, unchanged physics role.
- Server entity: a persistent fake server player (Fabric API FakePlayer on the fabric loaders, FakePlayerFactory-style construction on the forge loaders) in the same WorldServer the sim already binds to in singleplayer.
- Handler: a real server-side network handler (ServerGamePacketListenerImpl / NetHandlerPlayServer) for the fake player over a local in-memory channel, so processPlayer-era logic runs unmodified.
- Wire: two ordered queues owned by the sim loop, clientbound and serverbound, drained at fixed points below. No netty threads are involved during simulation.

Per-tick sequence for tick N:

1. Apply pending clientbound effects queued at the end of tick N-1 to the client entity (velocity sets, position corrections, world-visible block results are already in the world). This models packet-queue drain before the client tick [verify: client apply boundary per version].
2. If a position correction was applied and the version uses teleport IDs, synthesize the accept packet and the follow-up move packet the real client sends, before any other serverbound traffic for this tick [verify: modern ack flow; without this the handler freezes movement processing and the pair deadlocks after the first rubber-band].
3. Set inputs and rotation for the tick, then, on a recorded right click, synthesize the use-item-on packet and hand it through the real interaction manager before the client entity ticks: the crosshair ray uses the pre-tick eye position with the tick's freshly applied yaw and pitch fold (see section 13 item 14 for the vanilla ordering this mirrors), and applying the activation in the shared world before the movement tick doubles as the real client's instant prediction, so the same tick's movement already sees the new collision shape. Any teleport ack synthesized in step 2 drains ahead of the use packet, preserving the real accept-before-use arrival order, since the handler drops interactions while a teleport is unacknowledged. Then tick the client entity (existing path: setInput, applyTickEffects, applyYaw, tickEntity).
4. Synthesize the serverbound traffic the real client would emit for this tick: the move packet with end-of-tick position, rotation, and onGround; the per-tick input-state packet on versions that send it (1.21.2+) [verify].
5. Drain the serverbound queue through the handler synchronously, then run the server entity's per-tick update to the extent the handler does not already (damage bookkeeping, velocityChanged flush) [verify: which parts of the server player tick are handler-driven vs entity-tick-driven per version].
6. Collect everything the handler and server entity emitted (velocity packet, position correction, block changes, damage events) into the clientbound queue for step 1 of tick N+1, and append each to the run's event log.

The canonical interleave is thus: the server processes tick N's packets immediately after tick N; its effects land on the client at the start of tick N+1. Real singleplayer runs client and server on separate threads where this round trip is the common case but can jitter under load; the pair fixes the common case as the deterministic canonical timing. Playback against the real integrated server remains the place where real-timing behavior is observed (section 9).

## 3. Determinism

One loop drives both sides; there are no thread races and no wall-clock dependence inside a sim pass. The interleave is a fixed rule, not a measurement.

RNG invariant, replacing the withdrawn pinning requirement: the pair is deterministic because no supported mechanic reads RNG into an outcome. Movement integration is RNG-free. No-attacker damage consumes a random only for the hurt animation direction. The knockback gate draws a random and compares it against knockback resistance, which is 0.0 for players, so the branch is unconditionally taken and the draw is discarded. Sound and particle randoms sit in paths the sim entities already no-op. Consumption-only draws cannot desync anything; stream position is irrelevant when nothing reads it into an outcome. The invariant must be re-checked when a new mechanic enters scope (arrow spread is the classic counterexample if bow use is ever supported); until then, checkpoints capture no RNG state.

## 4. Checkpoints and the world journal

A checkpoint grows from one part to three:

1. Client entity scalars: the existing Checkpoint fields, unchanged.
2. Server-side scalars: position, motion, fallDistance, onGround, damage bookkeeping (hurtResistantTime and hurtTime gate repeat damage), health (pinned, see section 9), plus the handler's own fields: pending teleport state and ID, last-good position, floating-tick counters on versions that kick for flying [verify: enumerate per version]. Order of thirty scalars, same save/restore shape as today. Restore follows the existing pattern: reset both sides to the clean baseline, then overlay the captured scalars.
3. The world journal: every block mutation the sim causes, recorded as (tick, pos, stateBefore, stateAfter). Restore-to-tick-N means revert all journaled mutations and replay the journal prefix up to N. The journal is what reconciles observability with resimulation: the world permanently shows the net effect of the most recent pass, and any resim from any checkpoint first rewinds it.

Flicker-free application, so per-keystroke resims do not strobe the world for the player: during a pass, mutations are applied to the WorldServer with update-suppressed, no-notify flags (silent, invisible to the real client, but live for both sim entities, which read the same world). At pass end, the loop diffs the pass's net journal against the previous pass's net journal and sends client notifications only for positions whose final state changed. The player sees the trapdoor open exactly when the TAS's net outcome changes, not on every intermediate resim. Mutations and the end-of-pass notify run inside a short window synchronized with the server thread; the sim already reads the WorldServer cross-thread, but writes get the synchronization reads never had.

Journal lifecycle and persistence: the net-effect view is session-local; the world on disk must always keep the hand-authored state, or a TAS loaded in a later session finds its interactable blocks pre-toggled and every recorded click lands inverted. The journal therefore reverts fully, with client notification, whenever its pair is disposed (TAS load or new, undo restore, world change, paired toggle off) and on server stop before the levels save. The accepted residual leak is an autosave followed by a crash, which can persist the net effect without a clean stop; the fix is manual.

The checkpoint remains expressible for one structural reason worth stating: the pair has no hidden inputs. Every state change flows through the loop (inputs, synthesized packets, journaled mutations), so the state that must be captured is enumerable, and the resume-equals-full-run property stays testable (section 11).

## 5. World interaction scope

v1 supports instant-state interactions: trapdoors, doors, fence gates, levers-as-state (any activation whose entire effect is a block state swap at click time). This covers the block interaction ticket completely: a recorded right click on tick N flips the block inside the pass, the path after N sees the new collision shape, and the manual flip-and-resimulate workflow disappears.

Explicitly deferred: scheduled-tick blocks (buttons popping back, repeaters, any redstone cascade). Their timers live in the world's scheduled-tick queue, which advances with the real server clock, not sim ticks, and cannot be stepped in sim time inside the shared world without affecting reality. Supporting them faithfully needs virtualized scheduled ticks and is out of scope until a concrete need exists.

Interaction fidelity: clicks route through the real interaction manager, so reach and face validation are whatever the server actually enforces. The sim does not second-guess whether a click "should" work; if the server rejects it, the rejection is the result, and it appears in the event log.

Block placement and breaking are out of scope: the fake player's hand is deliberately empty and the input rows record no held item, so the pair cannot know a click would place, let alone what block. Supporting placement would require an item and inventory model in the input data; ruled out for now as not worth the complexity.

## 6. Performance

Budget: the addition per tick is the handler's move processing, whose dominant cost is one extra collision pass (the handler replays the reported move for its checks [verify]), plus interaction handling on click ticks only. Roughly 2x today's collision work per tick; current full-run resims cost low single-digit milliseconds, so the pair stays well inside per-frame budget for the resimulate-on-every-edit workflow. Chunk paging is unchanged, both entities read the already-preloaded WorldServer.

The real performance risks are structural, and they are rules, not options:

1. The pair is persistent across resims. Never spawn or despawn the fake server player per pass; construct once, reposition via checkpoint restore, exactly as the client entity works today.
2. The fake player must never register with the entity tracker or the player list, or the integrated server streams packets about it to the real client every pass.
3. No collisions, no AI targeting, no stat or advancement triggers, no sleep counting: the server-side mirror of the isolation SimulatorEntity and GhostPlayerEntity already implement client-side.

Two modern-specific requirements: the teleport-ack handshake (section 2 step 2) and the per-tick input-state packets since 1.21.2. One honest expectation to set: emergent behavior on 26.2 is modern behavior. Modern fall bookkeeping, movement validation, and slime handling differ from 1.8.9, so the pair will surface whatever desync tech exists on 26.2, which is not necessarily the 1.8.9 folklore from the wiki and community spreadsheets. "Does not reproduce the 1.8.9 slime boost on 26.2" is an expected outcome, not a bug.

Maintenance note: the pair touches more MC surface than the movement sim (handler internals, packet shapes), and loader-fabric tracks latest MC. The thin-loader rule below is what keeps each MC bump cheap.

## 8. Module placement and ports

Core stays Minecraft-free. Core gains: the event log data model (section 10), the extended checkpoint carrier shape (opaque server-side payload alongside the existing one), and whatever LazyEntitySimulator needs to sequence steps 1-6 abstractly. Loaders implement the pair behind the existing port pattern: entity construction, handler wiring, packet synthesis, journal application. The journal's block states are MC types and stay loader-side; core sees only counts and positions for UI.

The paired sim is opt-in, permanently: a Settings toggle (field on Settings, checkbox row in SettingsModal, persisted like allowDamage, default off), and the single-entity sim stays the default simulator on every loader. Consequences: toggling the setting must retrigger Application.runSimulation() like any input change; with the toggle off, behavior is exactly today's (no fake player constructed, no journal, no event log); and both sim paths are maintained side by side, which makes the section 11 parity gate a standing invariant between them, not a one-time promotion gate.

The toggle is gated by a confirmation modal (the ui/theme/Modal pattern) and the setting only changes on confirm; cancel leaves it untouched, so the SettingsModal checkbox defers its assignment instead of applying immediately like other rows. Both directions show: "WARNING: this resimulates your file from the beginning." (switching sim paths invalidates every checkpoint, so the next run is a full resim from tick 0). Enabling additionally warns that the fake server player can interact with and modify the world (block interactions the TAS performs, damage side effects, everything section 5 allows). Disabling additionally reverts the world journal's net effects before the resim, so the world rewinds to its unmodified state rather than stranding the last pass's mutations, and the modal says so.

## 9. Interplay

Solver: ExactJumpModel remains a byte-exact X/Z replica of client movement and knows nothing of server events. Solver work treats server-event ticks as segment boundaries, taking resume states from the paired sim, consistent with existing segmentation. Solving across an event (choosing inputs so that a damage boost lands) is future work and out of scope here.

Playback: unchanged in role, strengthened in meaning. Playback drives the real client and real integrated server, so it is the ground-truth check on the canonical interleave: where playback diverges from the pair, either a [verify] claim was wrong (fix the pair) or real thread jitter picked a non-canonical timing (expected, rare, and worth logging). The feature/allow-damage branch's playback-side pieces remain relevant: the real player's damage gating during playback, and health pinning. The branch's single-entity sim approach (letting SimulatorEntity take damage) is superseded by this design and should not merge as a sim feature.

Health pinning: the fake server player takes damage for real (that is the mechanism under study) but must never die or accumulate hunger effects; the setHealth-clamps-to-max override from feature/allow-damage carries over to the server entity.

Damage toggle: pairedDamage (default on) selects the server's damage policy while the pair stays live. Off models a server that cancels all damage: the fake player's hurtServer returns false before vanilla runs, so no damage ruling, no hurtMarked, and therefore no damage velocity flush and no slime damage boost, while plain restitution bounces remain. During replay the real player mirrors the same policy for ALL damage sources, not just fall (corrected 2026-08-16 after in-game QA: the original wiring suppressed only fall damage, so fire and lava still ruled on the real player with the toggle off, hurt animation and velocity flush included, desyncing the replay from a pair that predicted nothing): the fabric loaders cancel LivingEntity.hurtServer at HEAD for the local player, matching the fake player's gate placement, and the Forge loaders widen their LivingAttackEvent cancel from fall-only to all sources. The suppression condition is playback running and NOT (paired on and pairedDamage on), the same condition the fall gate always had: paired off (second correction, same day, user QA) also suppresses all damage, because the client-sided sim models no damage at all, so any real damage effect during a legacy replay is a guaranteed desync; the earlier fall-only legacy behavior was simply the incomplete version of the same intent. Real damage on the real player during replay therefore exists in exactly one mode: paired on with pairedDamage on. Movement checks and their corrections are independent of damage and always apply in both modes. Toggling resimulates the file through the same apply path as the paired toggle.

Replay world state: the world between passes shows the net effect of the most recent pass (section 4), which is the wrong starting state for a replay whose recorded clicks toggle those very blocks. At replay start the journal rewinds, applying after-states for entries before the replay's start tick and before-states for the rest, and notifies the real client (its prediction needs the rewound collision shapes); the replay's own clicks then mutate the world for real, outside the journal. At replay end the journal re-applies every entry's after-state and notifies again, restoring the net-effect invariant and erasing any drift a desynced or aborted replay left on journaled positions. The journal entries themselves are never truncated by a replay, so the sim's baseline stays stable. Blocks the player places during a replay (a real click while holding a block) are deliberately left in the world: they sit on positions the journal never tracked, and reverting them without restoring the consumed items would require inventory tracking (section 5 ruling). Replaying with an empty hand avoids the litter entirely.

## 10. Diagnostic event log

The pair emits a per-run log of server-originating events: (tick, kind, payload), where kind is one of velocity-set, position-correction, damage-ruled, block-changed, interaction-rejected. Surfaced in the UI alongside the tick list, this is how a TASer goes from "the entity behaved strangely at tick 14" to understanding the tech they just stumbled into: the log says the server ruled fall damage on tick 14 and set velocity on tick 15, without anyone having predicted it. The log is output only; nothing in the sim consumes it. It doubles later as the robustness tool (re-run with a shifted interleave and diff the logs), but nothing in v1 depends on that.

## 11. Verification gates

1. Baseline parity (the hard gate): on runs where the event log is empty, the paired sim's client trajectory is byte-identical to the single-entity sim, on every loader that ships the toggle, and it stays that way for as long as both paths exist (section 8 makes this a standing invariant, since the paired sim is permanently opt-in). The pair must not perturb the no-event baseline.
2. Liveness: a run containing a position correction continues past it (proves the teleport-ack synthesis); a run containing damage continues with pinned health.
3. Slime edge case: an edge landing constructed so client and server samples straddle the slime edge produces bounce plus damage plus a velocity-set event in the log, and the resulting trajectory matches an instrumented singleplayer playback of the same inputs under canonical timing.
4. Trapdoor case: a recorded right click flips the trapdoor mid-pass, the post-flip path uses the new collision shape, the world shows the flip after the pass, and a later resim with the click removed restores the world (journal revert).
5. Checkpoint equivalence: resuming from a checkpoint taken after any event (damage, correction, block change) reproduces the full run's suffix byte-exactly, extending the existing resume test pattern across all three checkpoint parts.
6. Performance: full-run resim wall time under the paired sim stays within 3x the single-entity sim on the same run (budget says ~2x; the gate leaves headroom, and a breach means a structural rule in section 6 broke).

## 12. Open questions

1. Local-channel wiring per version: constructing a handler without a real connection differs per loader family; the fabric FakePlayer helps, the forge loaders need the FG-era equivalent spelled out during [verify].
2. Sound and particle suppression for server-side interactions: routing clicks through the real interaction manager plays activation sounds to nearby players; per-resim replay would spam them. Proposed: suppress during passes, emit once at end-of-pass when the net journal changes, mirroring the block-notify diffing.
3. Ghost-block tech: some desync glitches require the client and server worlds to disagree about block state. Both pair entities read the same WorldServer in v1, so that class is out of scope; supporting it would need a diverged client world view and is a separate design.
4. Scheduled-tick virtualization (section 5 deferral): whether a future version can step a private scheduled-tick queue for sim-owned mutations without touching the world's real queue.
5. Whether the client entity should tick against the WorldClient instead of the WorldServer for maximal client fidelity: today's WorldServer binding exists for reliable chunk paging and is kept as an accepted approximation; revisit only if a [verify] pass shows a client-world-dependent behavior that matters.

## 13. 26.2 verification record (2026-08-14)

Every [verify] claim was checked against the decompiled 26.2 sources before the loader-fabric implementation. Confirmations and corrections:

1. Fall sample (section 0): both halves sample getOnPosLegacy(), which is getOnPos(0.2F); getOnPos handles the fence special case internally. Inside Entity.move the checkFallDamage call runs only when the entity is local-instance authoritative, so the handler's explicit doCheckFallDamage(clientDeltaMovement, packet.isOnGround()) at the reported position is the server's fall damage path. CORRECTED by in-game QA (2026-08-14): the bounce is gated by canSimulateMovement, and Player overrides that to true on the server side, so the move replay DOES run restitution on the server player; Player.isEffectiveAi is also true server-side, so the server player's own aiStep integrates travel (gravity, drag) every tick even though its position is client-authoritative. The server therefore keeps a genuine self-integrating motion accumulator; see item 13.
2. Bounce (section 0): on 26.2 the bounce is not the 1.8 motionY inversion; it is a generalized restitution system (Entity.restituteMovementAfterCollisions) with per-block bounciness, gravity compensation and drag, gated on isSuppressingBounce and the SUPPRESSES_BOUNCE tag. SlimeBlock.fallOn still negates fall damage via a 0.0 damage multiplier unless the entity suppresses bounce. The section 7 expectation stands: 26.2 emergent behavior is modern behavior.
3. Velocity flush (section 0/2 step 5): hurtMarked is set in LivingEntity.hurtServer for any impactful damage; the flush lives in ServerEntity.sendChanges (the tracker), which sends ClientboundSetEntityMotionPacket(entity) to tracking players and self. Since the pair's fake player is untracked by design, the loop emulates the flush: after the level-half tick, if hurtMarked, clear it and queue the packet built from the server entity's current motion. Payload claim confirmed.
4. Teleport ack (section 2 step 2): confirmed, including the deadlock. While awaitingPositionFromClient is non-null the handler ignores every move packet (rotation only) and re-teleports every 20 handler ticks; handleUseItemOn also drops interactions during that window. The real client answers ClientboundPlayerPositionPacket by applying position, velocity and rotation per the relatives set, then sending ServerboundAcceptTeleportationPacket(id) plus an out-of-band PosRot with onGround=false, horizontalCollision=false, without touching its move-packet bookkeeping. The pair synthesizes exactly that.
5. Client emission (section 2 step 4): the input-state packet is sent only when key presses changed since the last send, before the move packet. Move packets use the 2.0E-4 length threshold (squared compare) or a 20-tick reminder, rotation deltas, StatusOnly on onGround or horizontalCollision flips, and carry horizontalCollision since 1.21.2. Sprint syncs via ServerboundPlayerCommandPacket START/STOP_SPRINTING; the handler ignores the entity id in it.
6. Movement checks (section 0): moved-too-quickly is skipped for the singleplayer owner and gated by the PLAYER_MOVEMENT_CHECK gamerule. Moved-wrongly (0.0625 threshold after the move replay) applies except during sleep, creative, spectator and post-impulse grace, and is NOT owner-gated: it is the singleplayer flavor of the lagback. CORRECTED by in-game QA (2026-08-14): the pair's handler must report isSingleplayerOwner as true so the fake player gets exactly the owner's check set (moved-wrongly yes, moved-too-quickly no, keepalive not enforced); a non-owner handler applies a stricter check set than the real singleplayer connection ever sees.
7. Keepalive: the handler sends keepalives on wall-clock cadence to non-owner connections and disconnects on timeout. With the handler reporting isSingleplayerOwner (item 6 correction) keepalives are never enforced against the pair; the ack synthesis stays as a defensive path for loader ports whose owner semantics differ, and the handler's disconnect is no-op'd so nothing can kill the pair.
8. Server tick order and step 5 split: per MinecraftServer.tickChildren the levels tick before the connections. ServerPlayer.tick (level half) does tickClientLoadTimeout, gameMode.tick and invulnerableTime; the handler's tick runs doTick, which on 26.2 is the full entity tick (super.tick with hurtTime, baseTick, aiStep) plus food and bookkeeping, then snaps position back and handles the floating counters and knownMovePacketCount. The pair drains packets, then calls sp.tick(), flushes hurtMarked, then handler.tick().
9. Client-loaded gate: move and interaction packets are dropped until hasClientLoaded(); the pair synthesizes ServerboundPlayerLoadedPacket once at construction.
10. Interaction (section 5): handleUseItemOn acks the sequence, validates server-side reach (isWithinBlockInteractionRange(pos, 1.0)) and hit-vec sanity, checks mayInteract, routes through gameMode.useItemOn, and always sends two revert ClientboundBlockUpdatePackets (dropped by the pair; the world is shared).
11. Fabric API FakePlayer: confirmed as the wiring reference (ServerGamePacketListenerImpl over a Connection(PacketFlow.CLIENTBOUND) stub with CommonListenerCookie.createInitial) but unusable directly: it is unconditionally invulnerable and its listener drops every clientbound packet. The pair uses its own ServerPlayer subclass and handler.
12. Implementation choices the record should own: CriteriaTriggers are neutralized via PlayerAdvancements.clearTriggers() on the fake player (grants would broadcast chat); ChunkMap.move is cancelled for the fake player, since it would otherwise register player chunk tickets and entity-tracking state (section 6 rule 2); the right-click cadence is modeled as press edge plus a 4-tick held retrigger, a tick-based approximation of the client's frame-based rightClickDelay; ServerLevel sounds and game events are suppressed while a pass window is open; the fake player is pinned to survival via the widened ServerPlayerGameMode.setGameModeForPlayer rather than ServerPlayer.setGameMode, because the public path broadcasts a ClientboundPlayerInfoUpdatePacket about the fake player to every real client (section 6 rule 2 again: the pair must never leak into the real client's player-info state).
13. The modern slime damage boost, established from in-game QA logs (real playback vs pair, byte-identical through the landing tick): the server player's deltaMovement is a self-integrating accumulator (item 1 correction). On a slime landing the move replay's restitution bounces that accumulator, the post-snap fall ruling can simultaneously rule damage when its own sample straddles onto the neighbor block, and the server motion reaches the client as a SetEntityMotionPacket that overwrites the client's motion at the next tick boundary; the observed real boost value sat exactly on the LpVec3 quantization grid, proving the packet mechanism and the interleave timing. Consequences for the pair: clientbound motion payloads must be quantized through LpVec3 at apply time (the wire does this for real clients; captured packet objects bypass it), and the accumulator's initial conditions must mirror real playback (the start teleport seeds deltaMovement with the start velocity, the server player is airborne-unknown after the teleport, and the two warmup ticks integrate the accumulator before row 0). The accumulator is history-sensitive, so any remaining boost-magnitude mismatch between pair and playback is an accumulator-state divergence, not a mechanism gap.
14. Click timing (section 2 step 3), corrected by in-game QA (trapdoor clicks raycast post-tick missed blocks the real replay hit): Minecraft.tick recomputes the crosshair pick with this.pick(1.0F) before handleKeybinds and ticks entities only afterwards, and playback applies the row's yaw and pitch during START_CLIENT_TICK, which fires at the head of Minecraft.tick before that pick. A click recorded on row N therefore raycasts from the post-tick-N-1 eye position with row N's rotation, and startUseItem applies the block activation as client prediction before the movement tick, so tick N's movement sees the new collision shape. The pair mirrors this by folding pitch and synthesizing the click at the head of the tick, handling the use packet through the interaction manager immediately instead of queueing it behind the movement drain.
15. Fire ticks (found by log QA 2026-08-16: resim paths diverged from the human replay at the first onFire ruling, and [PC-PAIR] logged damage-ruled onFire at T1/T2 of fresh passes, at the start position, before any fire contact in that pass): Entity.remainingFireTicks persists on the fake server player across passes and checkpoint restores. Lava ignites for 300 ticks, which outlives most runs, and baseTick rules 1.0 onFire damage whenever remainingFireTicks % 20 == 0 outside lava, so a stale counter shifts the damage rhythm to different absolute ticks each pass, and every mistimed ruling's hurtMarked flush overwrites the client's motion at the next tick boundary (the T21 divergence class: vertical motion stomped, horizontal motion zeroed mid-jump). ## 15. Lockstep replay (2026-08-15)

Problem: the paired sim's canonical interleave is deterministic, but a real replay is not. The integrated server runs on its own thread with unconstrained phase relative to the client's tick loop, so a server effect computed for tick T (damage velocity flush, lagback correction) usually reaches the client before tick N+1 but rarely a tick later, and the run desyncs off the path. The race is two-sided: the client's tick-N move packet can also reach the server after tick T started, shifting the server's fall bookkeeping by a tick. Pure-movement replays are unaffected; only server-injected effects carry the risk.

Decision: during playback, make the two threads take strict turns instead of moving the server onto the client thread. The server stays on its own thread (every isSameThread contract, executor and chunk-IO path keeps working); a gate parks its tick until the client releases exactly one tick per client tick. Semantically the server tick becomes a subroutine of the client tick; physically nothing moves. Opt-in via Settings.lockstepReplay ("Lockstep replay" under Playback > Player, default off), singleplayer only, engaged from playback start to stop.

Per-client-tick protocol (ReplayLockstep): (1) serverbound flush: send a magic-id ServerboundPingRequestPacket and spin until its pong; FIFO on the local channel proves every packet the client tick sent has passed the server's netty handler and is queued. (2) grant one tick permit; the gate (mixin at the server tick entry) consumes it and the server runs exactly one tick. (3) spin until the completion counter (mixin at tick return) advances. (4) clientbound flush: second ping; its pong is written by the server's netty-inline handlePingRequest after every write the tick submitted, so on pong receipt all of tick T's packets are queued client-side and applied before tick N+1. Deferred split (2026-08-16, all three lockstep loaders, after 1.8.9 stutter QA): steps 1-2 run at the end-of-client-tick hook (sub-millisecond) and steps 3-4 moved to the head of the NEXT client tick, so the gated server tick overlaps the client's render frames instead of stretching the tick-carrying frame by a whole server tick; the pre-tick barrier then applies the queued packets itself before the tick runs (26.2: Minecraft.packetProcessor().processQueuedPackets() plus the widened runAllTasks; 1.21.3: the widened runAllTasks; both clients otherwise drain only once per FRAME before a loop of up to 10 catch-up ticks, so the manual pre-tick drain also closes the latent apply-order hole where a two-tick frame ran its second tick before the first tick's packets applied). Barrier spins yield-busy ~0.4ms before parking (Windows park granularity). The original blocking shape is retired on all loaders.

Determinism and liveness mechanics: while parked, the gate runs inside managedBlock, which pumps the server's executor tasks (server.execute hops from the bridge and the pair keep working, including blocking runOnServerThread joins) and self-wakes every 0.1ms via the bounded waitForTasks park. On permit consumption the gate fully drains the executor queue (pollTask loop, widened on 26.2) before letting the tick run: barrier step 1 only proves the client's packets are queued, and without the drain the release races the gate's poll cadence, so on 1.21.3 (where game packets are executor tasks) the move packet would usually be processed a full server tick late, shifting the damage ruling and motion flush and killing the damage boost; found by in-game QA 2026-08-15. 26.2 routes game packets through the tick-head PacketProcessor, which the released tick drains itself, but the release drain is kept identical on both loaders for the remaining executor traffic. The gate maintains nextTickTimeNanos and delayedTasksMaxNextTickTimeNanos slightly in the future while parked so haveTime stays true for task scheduling and no catch-up debt accrues (no tick bursts on disengage); on release both are reset to now, and a waitUntilNextTick head hook zeroes them so the post-tick wait returns immediately. Ping ids live above 0x504B4C4B00000000 so the pong-intercept mixin can consume ours (cancelling the debug ping monitor call) and pass vanilla's through. Pings are answered inline on the netty thread on both 26.2 and 1.21.3 (verified); the 26.2 server additionally routes game packets through the tick-head PacketProcessor while 1.21.3 handles them as executor tasks pumped between ticks, which is why the 26.2 gate sits at processPacketsAndTick head (before the drain) and the 1.21.3 gate at tickServer head.

Safety: the gate bypasses whenever the client is paused (IntegratedServer's own pause branch never reaches the gated super.tickServer on 1.21.3; on 26.2 the gate condition checks Minecraft.isPaused directly, the same cross-thread read vanilla makes) and whenever the server stops running. All client-side waits carry a 2s timeout that logs [PC-LOCKSTEP] and disengages rather than freezing the game; a barrier failure degrades to today's free-running behavior mid-replay. Engagement races at the start self-heal because each barrier re-reads the completion counter before granting. The start teleport window keeps its existing accepted approximation; determinism is guaranteed from the first full barrier on.

Cost, after the deferred split: the tick-carrying client frame pays only the serverbound flush round trip (sub-millisecond); the server tick itself runs concurrently with the render frames of the following interval, and the pre-tick barrier normally finds it long finished. A slow frame still slows the server identically instead of letting it run ahead, which also removes catch-up ticks as a secondary noise source. Implemented on all four loaders: loader-fabric (26.2), loader-fabric-1.21.3, loader-forge-1.8.9 (section 16 item 17 records the 1.8.9 mechanism deltas: Forge-event gate, futureTaskQueue pump, keepalive-magic markers via pipeline injection, pacing rewind) and loader-forge-1.12.2 (section 17 item 17: same Forge-event shape with long-id keepalive markers). In-game verification: 1.21.3 confirmed on the blocking shape, 1.8.9 confirmed on the deferred shape (determinism and smoothness); the fabric loaders' deferred shape is pending re-verification and 1.12.2 is unverified in-game. (1.12.2 update 2026-08-16: the section 17 tail records the in-game QA; boost confirmed, 22/22 replays clean at eps 1e-6.)
