# AGENTS.md

Shared guidance for AI coding agents and contributors. This is the canonical guide; `CLAUDE.md` imports it so Claude Code picks it up automatically, and other tools that read `AGENTS.md` get the same content. Navigation reference: where to find what, and the rules that must not break. For deeper context:
- `CONTEXT.md`: domain glossary. Decodes the Minecraft parkour and movement vocabulary (facing, direction, velocity, tier, neo, momentum, byte-exact, etc.). Read it first; almost none of these terms are in an LLM's training data.
- `docs/reference/mcpk/`: in-repo mirror of the Minecraft Parkour Wiki physics (movement formulas, constants, the sine table, collision order, block friction, status effects, tiers). The byte-exact ground truth this tool replicates; if code disagrees with a number there, the code is the bug.
- `docs/VISION.md`: north-star goal (two blocks in, full TAS out), the capability arc, design principles
- `docs/CODING_GUIDE.md`: module rules, where new code goes, port pattern, per-module toolchains
- `docs/research/`: angle-solver design record (includes the consolidated ILS notes), plus campaign and design records
- `CONTRIBUTING.md`: feature definition checklist, Conventional Commits, release-please flow


## Modules

```
core/                  Java 8.  ImGui-only UI/data + the angle solver. No MC, Fabric, Forge, or LWJGL imports.
forge-core/            Java 8.  Shared for both Forge loaders: lwjgl2/ ImGui bootstrap, sim/ sprint machine. No MC imports.
gpu/                   Java 8.  OpenCL (JOCL) implementation of core's SchedulePoolScreen port: the stratfinder's disk prefilter and affine screen on the graphics card. No MC imports; every loader bundles it, the CPU path stays the default.
loader-fabric/         Stonecutter tree, one source set for every Fabric target: 26.3 (Java 25, active), 1.21.3 (Java 21), 1.20.4 (Java 17). Loom, LWJGL3. MC-touching sim/render/mixins/entry point. Shared source under src/client/java; per-subsystem variants under src/renderpearl (26.x) vs src/blaze3d (1.21.3, 1.20.4) and src/sdl (26.3) vs src/glfw (older).
loader-forge/          Stonecutter tree, one source set for both Forge targets: 1.12.2 (active) and 1.8.9. Java 8, Unimined, LWJGL2. MC-touching code under src/main/java.
```

Each loader tree is a [Stonecutter](https://stonecutter.kikugie.dev/) project: `loader-<x>/stonecutter.gradle` is the controller, `loader-<x>/build.gradle` is the central build script applied to every version, `loader-<x>/versions/<mc>/gradle.properties` holds the per-target versions (MC, loader, Java), and `settings.gradle` lists the targets. MC API differences live in `//? if <cond> {` ... `//?} else {` ... `//?}` regions in the shared source (`//? if >=26.1`, `//? if >=1.21.2`, `//? if <1.12`, etc.); the raw file is the active version's code and the inactive branches are kept commented out by Stonecutter. Subsystems that differ by more than about a third of their lines get a version source set instead (the Fabric render and input variants above). A file never exists twice: a feature lands once in the shared source and ships in every target. Switch the active version with `./gradlew ":loader-fabric:Set active project to 1.20.4"` (and `Reset active project` before committing); `Refresh active project` re-comments regions after editing the inactive branches raw. `forge-core` holds the MC-free parts shared by the Forge targets.


## Core flow

1. **Inputs** (core): `InputOverlay` edits `InputData` (list of `InputRow`, one per tick: W/A/S/D/Jump/Sneak/Sprint/L-click/R-click + yaw/pitch + amplifiers).
2. **Simulation** (loader): the loader's `Simulator` port drives a `SimulatorEntity` (a real MC player subclass) tick by tick, recording positions.
3. **Visualization** (core + loader): `BoxController` (core) stores positions and decides what to draw, then calls the loader's `BoxRenderer` port for the actual GL draw. Start box is drag-to-reposition.

`Application` (core) is the singleton orchestrator that wires inputs, simulation, playback, and the solver. Any change to `InputData` or the start position must retrigger `Application.runSimulation()`. **Don't break this wiring.**

**Tick indexing:** `posX[t]` = position at the *start* of tick `t` (before that tick's inputs); box `k` shows pre-tick state. A constraint on tick `n` affects `posX[n]`; to constrain what tick `n`'s input *produces*, place the constraint on tick `n+1`.


## Build & Run

```bash
./gradlew chiseledBuild                        # every jar: loader-<x>/versions/<mc>/build/libs/pkc-<x>-<mc>-VERSION.jar
./gradlew :core:build                          # shared core lib (runs tableStyleCheck)
./gradlew :forge-core:build
./gradlew :gpu:build                           # OpenCL pool screen (JOCL); :gpu:probe lists the OpenCL devices and runs a vector add
./gradlew :loader-fabric:chiseledBuild         # pkc-fabric-26.3, pkc-fabric-1.21.3, pkc-fabric-1.20.4
./gradlew :loader-forge:chiseledBuild          # pkc-forge-1.12.2, pkc-forge-1.8.9
./gradlew :loader-fabric:26.3:build            # one target; / :runClient (same for :loader-fabric:1.21.3, :loader-fabric:1.20.4, :loader-forge:1.12.2, :loader-forge:1.8.9)
```

JDK 21 runs the Gradle daemon. `:runClient` auto-switches toolchain: Fabric uses JDK 25/21/17 per target (auto-provisioned via foojay), the Forge targets need a local JDK 8 (Adoptium). Only the active version of a tree compiles the raw shared source; the other targets compile Stonecutter's processed copy under `versions/<mc>/build/generated/stonecutter/`. Do not run `:runClient` while MC is already open (shared `run/` file + world locks deadlock). Per-module toolchain rules: `docs/CODING_GUIDE.md` § Rules per module.


## Tests

The real gate is `:core:test`. All tests are pure Java, no MC needed: the suite lives in `core/src/test/`, plus a small `forge-core/src/test/` set for the MC-free Forge ports (`:forge-core:test`, part of `:forge-core:build`, so the loaders CI job runs it on the Java 8 toolchain).

The default run excludes the expensive solver suites and finishes in seconds; `-PslowTests` includes them (a few minutes, `ProblemsTest` alone is most of it). The slow set is every class tagged with the JUnit category `de.legoshi.parkourcalc.SlowSolverTests` (9 classes as of the 2026-10-23 re-tier: `ProblemsTest`, `YawDirectionCrossCheckTest`, `NoTurnDriversTest`, `FoldReplayDriverTest`, `CertBnbDfFoldTest`, `TailScoreEquivalenceTest`, `FoldDriverEngineTest`, `WallHomotopyLadderTest`, `CertifiedBnbTest`; the heaviest are `YawDirectionCrossCheckTest` (about 280 s), `NoTurnDriversTest` (about 170 s), `FoldReplayDriverTest` and the `ProblemsTest` cases `solve/loopmm-3jump-lands` and `solve/loopmm-tight-t39`; grep the test sources for the category to list them). A class belongs in the slow tier only when it takes about 4 s or more on a CI runner; a quicker engine test stays untagged so the local fast run catches it (the re-tier moved `J008VelocityTest`, `YawOrderTest`, `DeepCheckTest`, `GraphRunnerTest`, `GraphPresetSolveTest`, `WrapWindowIlsTest`, `VelocityFinderConstraintTest` and `BuildHessianCapEquivalenceTest` to the fast suite, about 12 s together). CI runs `-PslowTests` on every push and PR, so nothing merges on the fast suite alone. To keep that under five minutes of wall clock, CI splits the core suite into balanced shards that run as parallel jobs on JDK 21 (`:core:test`), next to a separate loaders job that builds the jars (and runs the forge-core tests). The same shards run a second time on Java 8 (`:core:testJava8`) only on pull requests targeting `main`; every other push and PR gets one `java8-smoke` job instead, which runs the fast suite (with `CrossJvmDeterminismTest`) and the `closedform/` cases (`-Dpkc.problems='closedform/*'`) on Java 8. A solver budget that only misses on the slower Java 8 JIT is therefore caught at the weekly train, not on the feature PR (decided 2026-10-23). A shard is selected with `-PpkcShard=<i>/<n>`: `core/build.gradle` greedily assigns every test class (and every `ProblemsTest` case on its own, the class reads the `pkc.problems` system property) to the lightest shard; a parameterized class listed in `splitClasses()` there is cut into that many parts by case index instead (each part weighs its share of the class weight, the class reads `pkc.parts.<SimpleName>=<i,j>/<n>` through the test harness `ShardParts`, and `testWeights` sums the parts back into one class entry), which is how `YawDirectionCrossCheckTest` stops owning a whole shard, weighted by `core/test-weights.properties` (seconds from a measured run; unknown entries count as one second). `./gradlew :core:testShardPlan -PslowTests -PpkcShard=0/8` prints the plan; `./gradlew :core:testWeights` updates the weights file from `build/test-results/test`, or from the directory given with `-PpkcResults=<dir>` (for example the unpacked `test-results-jdk21-shard*` artifacts of a CI run): measured entries are replaced, entries the run did not cover are kept, entries for deleted classes or cases are dropped, and a very-slow class keeps at least one second so it never falls back to the 600 s an unmeasured very-slow class is booked at. Every CI shard prints its times as `test-time <name>=<seconds>` lines in the job log and uploads its result files. Refresh the weights when a heavy test is added or its budget changes. The shard count lives in the `SHARDS` env of `.github/workflows/build.yml`.

A heavier tier, `de.legoshi.parkourcalc.VerySlowSolverTests`, is excluded even under `-PslowTests` and runs only with `-PverySlowTests`. It holds the multi-minute engine-acceptance gates that need not run on every feature PR (currently `CertifiedBnbEngineTest`, the M2a certified-B&B gate; `PipelineShapeTest`, the M2b one-solve-path guard; and `NoTurnBendersTest`). CI adds `-PverySlowTests` only on pull requests targeting `main` (the weekly `dev` to `main` train and main hotfixes), so the very-slow gate still runs before anything reaches the release line.

```bash
./gradlew :core:test                          # fast suite; run after any change
./gradlew :core:test -PslowTests              # full suite; required when solver code changes
./gradlew :core:test -PslowTests -PverySlowTests  # + the very-slow engine-acceptance tier
./gradlew :core:testJava8                     # the same suite on a Java 8 launcher (the Forge loaders' JVM); honors -PslowTests
```

The solver's search path uses `StrictMath` (and `Angles.rad`/`Angles.deg` instead of `Math.toRadians`/`toDegrees`) so a solve is bit-identical on Java 8 and JDK 21; `CrossJvmDeterminismTest` pins golden hashes of the linear model and the closed form on one fixture, and CI runs it and the closed-form cases on Java 8 on every push (the whole suite on PRs to `main`) so the shipping runtime is exercised. Keep `Math.*` trig out of `core/.../anglesolver/` (the byte-exact `ExactJumpModel` and `McSineTable` are the deliberate exceptions: they mirror MC's own calls).

Run the full suite locally whenever the change touches solver code (`core/.../anglesolver/`, the model classes, velocity finder, graph) or the problem/capture resources; for anything else the fast suite is enough, CI covers the rest.

Add `-PverySlowTests` to that local run when your change could affect the **certified branch-and-bound** (`CertifiedBnb`, `SineTableGeometry`, `CertifiedBnbNode`, the certification bound/gap machinery) or the **pipeline stage sequence** (`BuiltinGraphs`, or any node's fire/guard/ordering that changes which stages run or in what order). CI runs that tier only on pull requests targeting `main` (the weekly `dev`-to-`main` train and main hotfixes), so on a feature-to-`dev` PR those two gates (`CertifiedBnbEngineTest`, `PipelineShapeTest`) are otherwise unchecked until the train, and a regression there would already have landed on `dev`. When in doubt on a solver change, run it; it adds a few minutes. Also run it before opening or approving a `dev`-to-`main` train PR, and before cutting a release.

When a new test class drives the solver engine on real captures and takes about 4 s or more, tag it `@Category(SlowSolverTests.class)` so the default run stays fast; if one such class grows past the other shards (more than about 150 s), add it to `splitClasses()` in `core/build.gradle` and filter its cases with `ShardParts`; if it is a multi-minute gate that need not run on every PR, tag it `@Category(VerySlowSolverTests.class)` instead.

- Folder-driven problem checks: `core/src/test/.../anglesolver/ProblemsTest.java` (parameterized over every folder under `problems/`: `solve/`, `closedform/`, `dualrecovery/`, `replay/`, `transitions/`, `planpath/`, `legal/`, `optimize/`, `multistart/`, `smooth/`, `freestart/`, `levelset/`, `ils/`, `translation/` and `gapattribution/`, one class per folder in `anglesolver/checks/`; a gate on one capture is a sidecar in a check folder, never a Java class that names the capture; sharing captures in `core/src/test/resources/captures/`; `problems/README.md` lists what each folder checks and the sidecar fields). Every fixture JSON under `captures/`, `problems/` and `hpk_human/` is one line with no BOM and no trailing newline. Map in `anglesolver/TESTS.md`.

Env-gated research tools (probes, dumps, screens, benches that skip unless a `PKC_*` env or `-Dpkc.*` property selects them) are not tests: they live in the `research` source set under `core/src/research/` (map and run commands in its README), run with `./gradlew :core:research --tests '*<Name>'`, and never join `:core:test` or the CI shards. `:core:check` compiles them. A new tool goes there, not under `src/test`.

The loader modules themselves have no test task (their code needs MC at runtime). The closest thing to loader coverage is `SprintMachineCaptureParityTest` in `forge-core`: it replays every 1.8.9 and 1.12.2 capture with recorded `debug` ticks through `PlayerSprintMachine` and checks the per-tick sprint flag and move inputs the real Forge `SimulatorEntity` produced (the loader samples them after the 0.98 damping of `EntityLivingBase.onLivingUpdate`). The Fabric sprint logic is MC's own `LocalPlayer`, so Fabric gets no such harness; `SimulatorEntity` on every target is still only verified in game. `tableStyleCheck` runs on `:core:check`/`build` (CI skips it with `-x tableStyleCheck`); it has a known false positive on `SolverWidgets`.


## Reading MC source (use local decompiled sources, don't fetch from the web)

To check an MC API surface, decompiled body, or local-var name, read the project's local decompiled sources. Web mirrors are often the wrong MC/MCP/yarn snapshot with decompiler-invented var names that won't match what compiles here.

Generate once:

```bash
./gradlew :loader-fabric:26.3:genSources :loader-fabric:1.21.3:genSources :loader-fabric:1.20.4:genSources :loader-forge:1.8.9:genSources :loader-forge:1.12.2:genSources
```

```
.gradle/unimined/net/minecraft/minecraft/1.8.9/.../mcp-stable-22-1.8.9-searge-1.8.9/...-sources.jar
.gradle/unimined/net/minecraft/minecraft/1.12.2/.../mcp-stable-39-1.12-searge-...-sources.jar
```

Unzip the relevant `-sources.jar` and grep for a single file (e.g. `EntityPlayerSP.java`, `LocalPlayer.java`). IntelliJ resolves these automatically on Ctrl-Click in any loader module.


## Critical patterns

- **Simulation is the single source of truth.** The loader's `SimulatorEntity` reproduces real MC movement; never approximate it. Divergence from MC is a bug, not an optimization. (The solver's `ExactJumpModel` is a separate byte-exact X/Z replica for the search inner loop, which cannot afford the MC-coupled entity; the entity is used for cheap post-Apply verify.)
- **Core stays Minecraft-free.** No `net.minecraft.*`, `net.fabricmc.*`, `net.minecraftforge.*`, or `org.lwjgl.*` in `core/`. If core needs world data, define a port in `core/.../ports/` and implement it loader-side (see `docs/CODING_GUIDE.md` § Ports).
- **Static wiring.** `Application` and the loader entry points use static fields/methods deliberately; the mod is a singleton and statics avoid passing refs across mixin/event boundaries.
- **Fabric ImGui input routing.** When the overlay is open, `KeyboardHandlerMixin` / `MouseHandlerMixin` (one pair per input variant, `src/sdl` and `src/glfw`) route events to ImGui; an `isUiFocused()` check gates pass-through, and box dragging is disabled while the UI is focused.
- **Fabric mixin lifecycle.** MC hooks go through mixins, not Fabric events (except `ClientTickEvents` for input polling). A new mixin must be added to the `mixins` list in `loader-fabric/build.gradle` (which generates `parkourcalculator.client.mixins.json` per target) or it silently won't apply. Forge loaders use the FML event bus + `ClientRegistry` keybinds instead.
- **imgui-java is pinned to 1.86.12** everywhere (`core/` compileOnly; loaders `include`/`shade`). The LWJGL2 ImGui shim was built against 1.86.11, whose native method surface is a strict subset of 1.86.12 (the only addition is the unused `ImGuiKnobs` extension), so the shim stays satisfied. 1.86.12 is the floor: it is the first release whose macOS native is a universal binary (x86_64 + arm64); 1.86.11 was x86_64-only and crashed Apple Silicon with an `UnsatisfiedLinkError`. Do not bump higher (e.g. 1.90.0 throws `NoSuchMethodError` against the shim).


## Branches & releases

`main` = released code only; `dev` = integration branch. Features branch off `dev` and require a quick in-game QA pass on every shipped jar whose code changed before merging (a shared-source change touches every target of that tree; core-only change: one jar suffices), so `dev` is always releasable. Fixes for released bugs branch off `main` and release immediately; merge `main` back into `dev` right after. A weekly cron opens the `dev` to `main` train PR; it must merge as a true merge commit, never squash. Full flow: `CONTRIBUTING.md`.


## Don't

- Add server-side code (client-only mod).
- Bypass `SimulatorEntity` with custom physics math.
- Import MC / Fabric / Forge / LWJGL types into `core/`.
- Break the simulation retrigger on input or start-position changes.
- Bump `core/`'s imgui-java compileOnly above 1.86.12 (or below it: 1.86.11 is x86_64-only on macOS and crashes Apple Silicon).
- Hand-edit `mod_version` in `gradle.properties`. It is bot-managed by release-please via the inline `# x-release-please-version` annotation, which MUST sit on the same line as the version (`mod_version=X.Y.Z # x-release-please-version`); on a preceding line, release-please's generic updater silently skips the file.
- Use em dashes in any writing in this repo (docs, code, commits). Use commas, semicolons, colons, or sentence breaks instead.
- **Add code comments.** Not javadocs, not inline notes, not "why" one-liners, nothing. Write the code only. The sole exceptions are comments already in the file (leave them) and a comment the user explicitly asks for in that request. If a name or structure needs explaining, pick a clearer name instead.
