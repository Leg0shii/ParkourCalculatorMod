## What the counters mean

The [summary](audited-2026-11-10/summary.json) reconciles 10568 newly consumed raw
movement choices: 9402 are screened, 8 are rejected by the initial-jump domain,
and 1158 enter the movement sources' seen sets. 1057 prefixes are expanded; that
includes 67 frame seeds. There are 104 pending prefixes, 5 deferred unknown nodes
and 59 emitted arrival programs. The counts reconcile as
`1158 - 104 - 5 - 59 + 67 = 1057`.

There are 240 numerical candidate evaluations, 187 solver API calls and 149 actual
worker launches; 38 calls return already-feasible seeds. These are different
units, not 10568 distinct complete routes or NLPs. Per-span query metrics sum
exactly to the run's 187 calls / 149 workers. 74 arrival records include physical
constraint variants of 59 emitted movement programs. Their copied evaluation
histories overlap; summing those histories is not a numerical-call count.

The zero workers on B1→B2 reflects a valid seed shortcut, not an unchecked

the issue is spending too long on late descendants of the first branch.

## Which candidates are actually kept?

The [complete admitted-program ledger](audited-2026-11-10/programs.csv) contains
1,158 rows, each reconstructed from its complete saved physical/search key.
Every reconstructed key is checked against the original. All 1,158 have ordinary
scalar movement histories; no stepping case survives admission in this run.

| Within the current anchor span | Admitted programs |
| --- | ---: |
| Grounded source preparations with no local jump yet |457 |
| Source preparations containing one or two same-block setup jumps |642 |
| Arrival at the next anchor without a same-block setup jump |27 |
| Arrival at the next anchor after source setup jumps |32 |

The 642 entries include different run placements before/after hops; they are not
642 different spatial routes or distinct hop impulses. For example, hop then
one run and one run then hop can have equal T/J/R/A but different schedules and
momentum. The key intentionally preserves that distinction. No within-frame
admitted programs differ only by their repair-state hash in this inventory.
That does not prove all constraint models or numerical requests are unique.

The fixture enables `normal` and `stepping`, permits 64 local/total run inputs,
uses a 200-input domain cap and solves each selected meaningful internal decision.
Its initial jump inputs are only 0/8. Later timings are generated by composing
one-input ordinary ground holds, source hops and transfer choices. Air duration
is derived from the scalar movement model; we do not enumerate discrete yaw
angles or independently choose every possible air tick. All earlier facings
remain continuous variables during each solve.

The global hard-jump latch restricts the final S→E transfer to one jump. It
deliberately leaves S→S setup hops eligible. Consequently a hard span still
contains many different preparation schedules. Named stepping cases additionally
branch over lower/higher blocks and side/corner conditions before screening.
Ceiling, ladder and generic intentional-wall-hit generators are not enabled by
this fixture. Some named stepping variants include case-required side contacts.

## Main generation waste: jointly impossible stepping pairs

The [native generator probe](audited-2026-11-10/generator-probe.json) enumerates
choices from the saved B3@28 prefix, with its hard history and all previous
facings free. It generates an ordinary source hop and one ground hold, plus:

- Eight `blip` choices involving lower B3 and higher B4, at relative input 11.
  `landing_wall_options` tries four X/Z sides, each with avoidance or a finite
  case contact.
- Four `corner_blip_up` choices for the same block pair, from two X signs times
  two Z signs, also at relative input 11.

All 12 are subsequently rejected by the existing required-interaction envelope
screen. The proposal has a contradiction at absolute state 39; the screen can
report the first earlier required contact because the entire envelope is already
contradictory. That does not mean B1 itself is the problematic choice.

The gap is in `stepping_generation.open_stepping_choices`: early gate calls test
lower and higher blocks separately against a free approach. They do not impose
the selected lower landing while testing the higher interaction. The conflicting
combination is discovered only after side/corner variants are constructed and
composed. Thus no stepping NLPs survive, yet B3→B4 still consumes 85% of raw
generation. The probe also constructs four impossible B7/B4 corner variants
while considering B5→B7.

This diagnostic proves the 12 rejections for the sampled prefix; the saved run
does not retain full profiles for every rejected raw choice. Its 9,028 B3→B4 raw
choices therefore cannot be retrospectively divided exactly by case from that
report alone. The 1,158 admitted-program inventory is complete.

## Main solver work: locally feasible but late source preparations

[Node records](audited-2026-11-10/nodes.csv) and
[query metrics](audited-2026-11-10/queries.csv) identify 114 worker launches for
same-block setup-hop feasibility: 12 on B2, 85 on B3 and 17 on B4. Only 35 worker
launches evaluate anchor arrivals or the final finish.

The search tries different takeoff inputs, holds before/after a source hop, and
sometimes a second source hop. It checks these when selected for descent,
because the configured internal-node cadence is 1. The hold prefixes themselves
do not launch NLPs. Different successful B3 arrivals open 13 incoming frames for
B3→B4, whose alternatives then open 31 frames for B4→B5.

The current finish bound is only a horizontal distance/speed relaxation. It does
not add the vertical flight costs of the remaining jumps. The scalar helper
gives ordinary-jump clocks 9, 10, 15, 9 for B2→B3→B4→B5→B7. For an ordinary
continuation, B3@38 therefore cannot finish before 72. Yet it is locally feasible
and the weaker horizontal bound admits it. The actual inventory includes B3
arrivals 38–49 after a B2 setup hop, which then create more downstream work.

These ordinary clocks are **not** a valid unconditional bound if an admitted
stepping/cancelled-jump alternative can shorten a span. A stronger bound must
account conservatively for the permitted mechanics. This audit does not silently
introduce a normal-jump-only restriction or disable useful source hops.

There are 240 evaluations across 173 base solve-model identities. Repeated base
models can resume preparation or explore different physical constraint variants;
they are not automatically duplicate NLPs. Successful internal nodes do not
retain every full numerical request body, so this report cannot certify that
all 149 worker calls were necessary or distinct. A future call trace should log
each exact request fingerprint before testing redundant-call hypotheses.

## Recommended next changes

1. Use the shared reachability helper to test lower/higher prerequisites jointly
   before enumerating side/corner variants. Preserve unknown Y for named probes;
   add nearby-block controls so valid stepping cases are retained.
2. Strengthen remaining time with minimum feasible transfer durations across the
   required-anchor chain, conservatively including admitted named mechanics.
   Reject late preparation nodes before solving them. Keep source hops available
   when they can still improve the finish or recover an infeasible harder jump.
3. Log exact numerical request identities during the next measured solve before
   deciding whether repeated base-model refinements can be removed.

These target earlier elimination of useless generation and solves while keeping
the requested DFS/anchor structure. This audit changes no production policy.

## Reproduce

From `standalone/` with the repository root on PYTHONPATH:

```sh
../.venv-guidance/bin/python -B autonomy/experiments/anchor-candidate-audit/audit.py \
  --input autonomy/experiments/anchor-runtime-profile/integrated-2026-11-10/combined-final-300s/report.json.gz \
  --output /path/to/new-audit
../.venv-guidance/bin/python -B autonomy/experiments/anchor-candidate-audit/probe.py \
  --input /path/to/new-audit/probe-contexts.json.gz \
  --output /path/to/new-audit/generator-probe.json
```

The probe also requires `PKC_RUN_TICKS_COMPILER` pointing at the existing native
compiler config. It calls scalar/Java helpers and linear screens, never IPOPT.

The follow-up plan's controls use pure existing scalar/generator helpers and
need neither a Java compiler process nor IPOPT:

```sh
../.venv-guidance/bin/python -B autonomy/experiments/anchor-candidate-audit/plan_probe.py \
  --contexts /path/to/new-audit/probe-contexts.json.gz \
  --output /path/to/new-plan-controls.json
```

Keep the repository root on PYTHONPATH. The script refuses an existing output
path so previous evidence is preserved. Its geometry diagnostics are not yet an
automatic family-wide duration certificate; that implementation is in the plan.
